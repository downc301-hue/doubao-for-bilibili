# 开发规范与作业流程

> 本文档定义项目开发的标准作业流程（SOP），所有参与者必须遵守。

---

## 一、作业标准流程

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  需求确认  │ →  │  架构设计  │ →  │  编码实现  │ →  │  测试验证  │ →  │  交付更新  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
      │               │               │               │               │
      ▼               ▼               ▼               ▼               ▼
  用户澄清需求     确定技术方案     遵循编码规范     核心逻辑必测    更新 HANDOFF
  拆解功能点       输出架构文档     小步提交         测试通过方可     同步状态文档
                                   及时更新文档     进入下一阶段
```

---

## 二、新功能开发步骤

1. **读取交接文件** → 确认当前状态和待办
2. **分析需求** → 理解业务逻辑，拆解为可实现的技术点
3. **设计方案** → 确定接口、数据结构、依赖关系
4. **编码实现** → 小步前进，每完成一个小功能就验证
5. **编写测试** → 核心逻辑必须有测试覆盖
6. **更新文档** → HANDOFF.md 和 project-state.md 必须同步更新
7. **提交代码** → 规范的 commit message

## 三、代码规范

### 3.1 命名约定

| 类型 | 格式 | 示例 |
|------|------|------|
| 变量/函数 | camelCase | `getUserInfo`, `isActive` |
| 类/接口 | PascalCase | `UserService`, `HttpResponse` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 文件 | kebab-case 或 PascalCase | `user-service.ts` / `UserService.java` |
| 目录 | kebab-case | `user-controller/` |

### 3.2 注释规范

- ✅ **写"为什么"**：注释说明这段代码存在的原因、设计决策的背景
- ❌ **不写"是什么"**：代码本身应该自解释，不要重复代码内容
- ❌ **不留废弃代码**：用版本控制系统管理历史，不要注释掉旧代码

### 3.3 函数设计

- 单一职责：一个函数只做一件事
- 参数不超过 3 个，超过则封装为对象
- 返回值明确，避免 `null` / `undefined` 的歧义（使用 Optional / Result 类型）

## 四、Git 提交规范

### 4.1 Commit Message 格式

```
type(scope): subject

body（可选）
```

### 4.2 Type 类型

| Type | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(auth): 添加微信登录` |
| `fix` | 修复 Bug | `fix(order): 修复支付回调重复处理` |
| `refactor` | 重构（不改变行为） | `refactor(user): 抽取公共校验逻辑` |
| `perf` | 性能优化 | `perf(list): 大数据量分页优化` |
| `test` | 新增/修改测试 | `test(auth): 补充登录单元测试` |
| `docs` | 文档变更 | `docs: 更新接口文档` |
| `chore` | 构建/工具/依赖 | `chore: 升级依赖版本` |

### 4.3 分支策略

- `main` — 主分支，保持可部署状态
- `feat/*` — 新功能分支
- `fix/*` — 修复分支
- 完成后合并回 `main`，删除临时分支

## 五、交接更新规范

### 5.1 何时更新 HANDOFF.md

- ✅ 完成一个阶段的开发（如：环境搭建完成、核心功能开发完成）
- ✅ 遇到阻塞性问题需要用户决策
- ✅ 准备结束当前对话
- ✅ 发现技术债或临时方案需要记录

### 5.2 更新哪些内容

| 场景 | 更新内容 |
|------|----------|
| 完成一个功能 | 勾选待办事项、更新进度阶段 |
| 开始新功能 | 在待办事项顶部添加新任务 |
| 遇到问题 | 记录到"已知问题"，更新中断位置 |
| 环境/依赖变更 | 更新技术栈表格 |

---

## 六、质量门禁

- [ ] 代码能正常运行，无报错
- [ ] 核心逻辑有测试覆盖
- [ ] 没有明显的安全隐患（硬编码密钥、SQL 注入等）
- [ ] HANDOFF.md 和 project-state.md 已同步更新
- [ ] Commit message 符合规范
